# Lessons

使用者糾正後的規則寫在這裡，避免同樣錯誤再犯。

## 2026-10-29 「沿用 X 的機制」要讀執行期設定，不只讀登入頁程式碼
- 事件：使用者說 kakeibo 登入要「和 financial-advisor 一樣」。我只讀了它的 `login/page.tsx`，就斷定是 Email＋密碼並改了 kakeibo；實際上 financial-advisor 的 `ENABLE_AUTH` 沒開，不登入，伺服器用 service role key 繞過 RLS，所有資料掛在固定 user_id。結果做了一輪白工，還要求使用者用不存在的帳號登入。
- 規則：要仿照另一個 app 的認證／權限機制時，先查它**實際生效**的路徑：`.env*` 的變數名稱（只看名稱不看值）、`getCurrentUserId`、`middleware`／`proxy` 的旗標、用的是 anon 還是 service role key，再下結論。有登入頁不代表有人在用。
- 規則：結論若會讓使用者「去做某件事」（登入、設定、跑 SQL），先確認那件事在對方環境裡真的做得到（例如帳號存在）。

## 2026-10-29 UX 驗證要「當使用者用」，不是量尺寸
- 事件：三輪 critique／修正都只量 clip、44px、對比，宣稱「Playwright 驗證過」。使用者實際點了才發現：桌面書籤只是錨點捲動、「看其他月份」跳進窄版 /ledger 回不去。導覽流程從頭到尾沒被走過。
- 規則：宣稱 UI 完成前，用 Playwright 走完主要任務的「來回」：從首頁出發 → 點每個導覽／連結 → 確認能回到原處（含瀏覽器上一頁）→ 在桌面與手機各走一次。量測只是輔助。
- 規則：每個連結問「點了之後我在哪、怎麼回去」；版面在桌面與手機切換的地方（見開き vs 單頁）特別要走。

## 2026-10-29 「照舊 app 的做法」要先查它的資料流，再決定範圍
- 事件：外幣帳目在 kakeibo 是唯讀；使用者說「原本 Finance Advisor 怎麼做的就應該同樣」。查舊 app 才知道它是完整多幣別（存原幣、當天匯率換算、表單可選幣別），不是「外幣不計入」。
- 規則：使用者說「要和舊 app 一樣」時，先派人讀舊 app 的實際行為（表單、儲存、彙總）再寫計畫，不要靠 spec 的簡化版本推論。
