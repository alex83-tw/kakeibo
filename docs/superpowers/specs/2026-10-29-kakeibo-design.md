## 1. 意圖與為什麼

使用者有一個既有的「financial-advisor」作品（`/Users/hungli/dev/personal/finance/financial-advisor`，Next.js + Supabase），想把核心功能拆成各自獨立的 App。kakeibo 是其中的「家計簿」：**每天打開記帳，看到每天的趨勢與預算，並強化會計、分類、預算、示警**。

**【決定】** 範圍只有收入、支出、預算消耗、現金流、記帳正確性。**不做**投資、資產、退休、負債、保險管理，也不依賴任何市場資料同步。

**【決定】** 名字 kakeibo＝日本「家計簿」。視覺從日本印刷家計簿（羽仁式）的文化出發，見第 8 節。

**【決定】** 共用既有 Supabase 資料庫，不搬資料。

## 2. 使用者與情境

**【決定】** 只有使用者本人。手機優先、每天用；電腦偶爾用，做月底檢視與對帳。語言為繁體中文（台灣）。

## 3. 目標、非目標、反目標

**目標**
- 三秒內記完一筆（支出、收入、轉帳）。
- 打開就知道：今天花了多少、這個月預算用到哪、有什麼需要處理。
- 帳是對的：每個帳戶的帳面餘額能與實際帳單對上，差異浮上來。
- 分類夠細、預算夠簡單（見第 5.3 節）。

**非目標（不做）**
- 投資、資產配置、退休、負債、保險的管理或試算。
- 現金流預測（月底資產預測、未來現金流）。月底「預估支出」屬預算進度，保留。
- 多使用者、分享、權限。
- 資料遷移或改寫舊帳目。

**反目標（技術上能用但算失敗）**
- 帳目數字與帳戶餘額、預算、對帳在不同畫面互相矛盾。
- 每個示警都是噪音（同一個閾值一個月響很多次）。
- 看起來像通用理財 app（圓角卡片、漸層、一堆圖示）。
- 為了好看讓字太小、點不到或對比不足。

## 4. 約束與技術

- **共用既有資料庫**：實際 schema 以線上資料庫為準（使用者說明為 `financial` schema，有 RLS）。舊 repo 的 migrations 只能當線索，**不可當權威**；開工前先讀線上 schema。
- **直接操作資料庫通常不可用**：一律寫成可審閱、可重複執行（idempotent）的 SQL 檔放 `migrations/`，由使用者自己執行；每次工作結束要列出「尚未執行的 migration」。查詢新欄位前先確認 migration 已跑；不可對尚不存在的 schema 寫查詢。
- 大量 UPDATE 的 SQL 要包 `BEGIN; … ROLLBACK;` 並附斷言 SELECT（列數、重複、外鍵），先乾跑再出 COMMIT 版；先傾印線上現況，不要用舊匯出。CJK 比對前先做 NFKC 正規化。更新腳本只能動需求指名的欄位。
- 不得讀取或使用儲存的憑證／金鑰；需要憑證的步驟請使用者手動執行。
- **技術棧【我的判斷】**（沿用舊 app，使用者未逐項簽核）：Next.js 16 App Router、TypeScript strict、Tailwind CSS 4 + Radix UI、React Query、Recharts（若用得到）、Supabase、Vercel、Vitest。UI 全繁中。舊 app 啟用 React Compiler（不手寫 useMemo／useCallback）。
- SSR：瀏覽器專用 API（`localStorage`、`window`）要防護，不可在伺服器渲染時崩潰。
- `supabaseAdmin` 會繞過 RLS：用它時**每個查詢都要自己加 `user_id` 條件**。
- 驗證流程：改 UI 後用 Playwright 真實瀏覽器操作（導覽、點擊、輸入、送出）再截圖；提交前跑 `tsc`、eslint、完整測試，回報實際通過數。

## 5. 功能規格

### 5.1 今日（首頁）【決定：今天優先】

由上而下：日期（漢字，例：二十八日 水曜）與**帳戶合計**（首屏、可點跳到帳戶）；今日支出合計；今日明細表（科目／摘要／帳戶／金額）；本月預算（已用 %、已用／預算、每日支出長條、預估月底）；注意；帳戶；底部固定「記一筆」。

- 每日長條是**單一控制項**（可拖曳、左右鍵、Home／End），上方即時顯示選到那天的日期與金額。不是 28 個按鈕。
- 注意區最多顯示三條，優先序：預算超支或預估超支 → 對帳差異 → 未歸類。每條 48px 高、連結點擊區 ≥ 44px。

### 5.2 帳本

月內每日收支表（日／科目・摘要／收入／支出），含週計與本月累計，今天以墨色粗框標示。

**【待補規格，示意稿沒畫】** 點日期進入「當日明細」：每筆可編輯、刪除；刪除有撤銷（沿用舊 app 的軟刪除 `deleted_at` 與約 5 秒復原語意）。這是記錯一筆時唯一的修正路徑，必須做。

### 5.3 分類與預算

- **【決定】兩層文字分類（主分類＋子分類）**，不做 ID 樹。**【決定】預算只設在主分類**；子分類只是明細標籤，不設預算、不示警。子分類預設「一般」（儲存為 `other`）。
- **預設分類【我的判斷，最終清單【待定】】**：支出主分類約 12 個（餐飲、交通、居住、日用購物、醫療保健、娛樂休閒、學習成長、人情社交、家庭、保險（僅作支出）、稅費、其他），合計約 60 個子分類；收入主分類 6 個（薪資、獎金、兼職副業、投資收益（只記錄不管理）、退稅補助、其他）。
- **改名／合併**：一個資料庫函式（RPC，SECURITY INVOKER）在 `accounting_entries`、`budget_plans`、`category_rules`、`recurring_rules` 一次改名或合併。`budget_plans` 有唯一鍵，合併時遇到衝突要把預算金額相加。**【我的判斷】** 舊帳目不改寫，維持「主分類／一般」；之後可選擇性用 `category_rules` 預覽後批次重新歸類（傾向不做）。
- 預算進度含 `rollover_amount`、`warning_threshold`。

### 5.4 記一筆

底部固定按鈕，升起輸入單：類型（支出／收入／轉帳）→ 金額 → 科目（轉帳改為轉出／轉入帳戶）→ 帳戶 → 日期（預設今日）→ 摘要（選填）→ 儲存。

- 轉帳**不計入收入與支出**，只移動帳戶餘額。
- 儲存後要有回饋（例：「已記錄 NT$1,500 轉帳」）並可撤銷。
- 常用科目／最近科目應排在前面（示意稿沒畫）。

### 5.5 帳戶、轉帳、對帳

- **【決定】** 記錄用哪個帳戶付出、進帳。帳戶種類：現金、銀行、電子支付（例：悠遊卡）、信用卡。
- 帳面餘額＝期初餘額＋各筆異動；信用卡以負數呈現（△）。舊帳目歸到「未指定」帳戶。
- 注意：舊 repo 的 `account_infos` 是「帳戶資訊備忘（銀行、券商、證件）」，**不是記帳帳戶**，不要拿來用；記帳帳戶需要新表。
- **對帳**：使用者輸入實際帳單餘額，系統比對帳面。**差＝帳面−帳單，用 △ 表示帳面較少**（信用卡 △3,150 − △2,830 ＝ △320，帳戶合計 68,270 − 68,590 ＝ △320，兩處同號）。白話一律寫「帳面比帳單多欠 320」。對上時顯示青緑「對上」。

### 5.6 示警

兩類，都不依賴市場資料：
- **預算層**：警告閾值、預估月底超支（進度預估：已用 ÷ 已過天數 × 當月天數）、每個閾值每月只提醒一次、每日摘要。
- **記帳層**：重複帳、漏記週期性項目、金額異常、未歸類、對帳差異。
- **投遞管道【我的判斷】**：先做 App 內「注意」清單；推播／Email 之後再說。使用者尚未決定。

### 5.7 現金流【決定】

本月收入、支出、淨額＋各帳戶目前餘額。**不做預測**。

### 5.8 設定

管理入口：預算、科目、帳戶、週期帳目、自動分類規則、匯入／匯出（CSV）。預算只列主分類。

## 6. 資料層

需要新增或調整（**開工前對照線上 schema 確認，以下是我讀舊 migrations 得到的線索**）：

## 8. 視覺系統（羽仁式家計簿）

定稿示意稿：`docs/superpowers/specs/assets/hani-sketch-v9.html`（靜態、假資料、可直接在瀏覽器開；內含 CSS 與少量 JS，是**視覺與互動參考，不是產品程式碼**）。

- **三色刷【決定】**：墨 `#1A1D1B`、朱 `#C13A2B`、青緑 `#2B7A68`。朱只用於「需要處理」（注意、差、預估超支）；青緑只用於「已對上」；其餘一律墨加網點。不可用顏色單獨傳達意思（一律附文字）。
- 紙 `#F7F7F3`；方眼格線只在左右邊距；內容區是每 36px 一條的行線；標題區鋪紙色蓋住行線，標題不壓在線上。
- 活版印刷語彙：書眉、直排欄標（今日／帳本／帳戶）、漢字日期、表罫（外 2px 內 1px）、合計雙底線、負數用 △、今天用墨色粗框。**不要蓋章**（使用者否決）。
- **書籤分頁**：手機頁面上緣四枚（今日／帳本／對帳／設定），電腦版左頁一枚、右頁三枚；**不顯示頁碼**【決定】。
- **字型**：Noto Serif TC（400／700）；數字用 Noto Serif 子集（它的數字等寬，Noto Serif TC 的數字是比例寬度，右對齊金額會參差），金額用 `tabular-nums`。四個字級：figure 2rem、title 1.25rem、body .9375rem、label .8125rem；**最小 13px**；小字字距 ≤ .15em；摘要 13px 灰色最多兩行；金額與 `NT$` 不可斷行；`line-break: strict`。載入策略：只載入用到的字重，不要整個載入。
- **電腦版**：見開き。左頁整月帳本（含每日趨勢長條），右頁今日、各主分類預算表、注意、對帳。
- 對比（已量測）：灰字 7.79:1、朱 5.00:1、青緑 4.78:1（皆過 AA，青緑最接近底線，不可再淡）。
- 示意稿**刻意沒畫**：電腦版的設定與記一筆、當日明細頁、各種選擇器、錯誤與空白狀態。這些由開發者依本文件與視覺系統延伸。

## 9. 驗收條件（critique 兩輪後留下的行為規格）

- 對帳符號慣例：全站一致「差＝帳面−帳單、△＝帳面較少」，並提供白話說明。
- 記一筆輸入單是**真正的對話框**：開啟時背景（書籤列、內容、dock）`inert`、`aria-modal="true"`、Tab 在框內循環、Esc 關閉並把焦點還給「記一筆」。
- 金額與帳單餘額只收數字（含逗號、△），非法輸入以行內文字加 `aria-live` 提示；空金額不可儲存並聚焦欄位；超長數字不可撐破版面。
- 每個互動目標 ≥ 44×44px；滑桿不得逐格以 `aria-live` 播報（用 `aria-valuetext`）。
- 儲存、刪除、對帳結果都要有可見回饋；刪除可撤銷。
- 手機寬度下，只在電腦版出現的控制項不得出現在 Tab 順序。
- 數字一致性測試：同一份資料在今日、帳本、對帳、現金流、電腦版各處的收入、支出、淨額、餘額、預算合計必須相等；以單元測試涵蓋台灣時區月界。

## 10. 補充預設與待定

### 10.0 審閱後使用者的回答【決定】

- **舊 financial-advisor 不再寫入**共用的表（只讀或已停用）。因此 kakeibo 可以直接擴充 `entry_type`、新增欄位，migration 不必向後相容舊 app 的寫入。開工前仍請對線上 schema 確認。
- **離線不需要**：網路不通時顯示失敗並保留輸入內容，恢復後可重送；不做本地佇列、樂觀更新或 PWA 快取。

### 10.1 builder 審閱後補上的預設（全部是【我的判斷】，可調整）

- **身分與登入**：沿用舊 app 同一個 Supabase 專案與認證方式（同一位使用者）；`user_id` 型別以線上 schema 為準（舊 repo 後來是 TEXT），RLS 比對 `auth.uid()`。正式環境**完全關閉** dev bypass，dev bypass 只在本機開發旗標下存在。
- **轉帳的資料模型**：一筆 `entry_type='transfer'` 的列，同時帶 `account_id`（轉出）與 `transfer_account_id`（轉入）。理由：一次撤銷、一次刪除，不會出現只剩一端的帳。轉帳不計入收入與支出。
- **期初餘額**：每個帳戶有 `opening_balance` 與 `opening_date`，由使用者在建立帳戶時填「截至某日的實際餘額」；只有 `opening_date` 當天及之後的異動計入帳面。舊帳目歸「未指定」帳戶，**不計入**帳戶合計，且只有在期初日之後仍有未指定帳目時才顯示在帳戶列表。
- **預算滾存與超支**：沿用舊 app 的語意：`rollover_amount` 是存進資料庫的值（不是即時推算）；`warning_threshold` 跟著每個主分類的預算設定；「超支」與「預估超支」都把滾存算進可用額度。判斷用 `ratio >= warning_threshold` 與 `ratio > 1`，不可只看 `> 1`（見第 7 節）。
- **示警預設門檻（可調）**：重複帳＝同日、同金額、同帳戶、同主分類的兩筆以上；金額異常＝高於該主分類近 6 個月單筆中位數的 3 倍且 ≥ NT$1,000；漏記週期項目＝週期規則到期日已過 3 天仍無對應帳目，**只提醒、不自動補記**；未歸類＝主分類為空，或主分類「其他」加子分類「一般」的帳目（開發者可微調）。
- **對帳差異**：只顯示差異，第一版**不建立調整分錄**。注意區的對帳差異在使用者重新輸入帳單餘額且對上後消失；使用者也可以補記遺漏的一筆後重新對帳。
- **多幣別**：第一版只支援 TWD。既有非 TWD 的列不阻擋顯示，但**排除**於帳戶餘額、預算與數字一致性測試之外，並在帳本以「未納入」標示。
- **專案位置與技術棧**：kakeibo 是獨立的新儲存庫（`/Users/hungli/dev/personal/finance/kakeibo`，需先 `git init`），不放進舊 monorepo。技術棧沿用第 4 節預設，使用者尚未逐項簽核。

### 10.2 仍待定與留給開發者

- 最終預設分類清單與子分類。
- 舊帳目是否批次重新歸類（傾向不做）。
- 記帳帳戶的 schema 細節、期初餘額如何設定、「未指定」帳戶的處理。
- 示警的投遞管道（第 5.6 節）。
- 預設主分類預算的初始值（示意稿的 52,000 只是假資料）。

## 11. 建議的開發順序（讓開發者參考，可調整）

1. 讀線上 schema，列出與本文件的差異；寫 migrations（帳戶表、transfer、對帳紀錄、必要的欄位）給使用者審閱執行。
2. 資料層與純函式（月界、預算進度、帳面餘額、對帳差異）＋單元測試。
3. 記一筆與帳本（含編輯、刪除、撤銷）。
4. 今日首頁、預算與示警。
5. 帳戶、轉帳、對帳。
6. 設定與分類管理（改名／合併 RPC）。
7. 電腦版見開き。
8. 以 Playwright 逐頁驗收第 9 節。
